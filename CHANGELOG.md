## 0.1.0 (Unreleased)

BREAKING CHANGES:

* data-source/agentops_worker_catalog: Removed the `configurable_model` attribute. The control plane no longer returns it, so the regenerated client has no field to read: a configuration referencing `agentops_worker_catalog.*.configurable_model` stops planning on upgrade. Drop the reference — there is no replacement attribute.
* resource/agentops_grader_config: The grader-config API has been removed from the control plane. The resource type is still registered so an existing state can be read, but create and update now fail; remove it from your configuration and from state (`terraform state rm`). Its `docs/resources/grader_config.md` page no longer carries usage or import examples.
* resource/agentops_agent, resource/agentops_self_hosted_catalog_deployment: A `terraform destroy` that cannot delete the agent now fails instead of succeeding while the agent survives. `DELETE /agents/{id}` is gated on the `self_hosted_agent_lifecycle` feature, which is **off by default**, and answers `404` while it is shut — previously read as "already gone", which dropped a live agent, still holding a worker token, out of state. The destroy now falls back to the ungated delete the AgentOps UI uses, which the control plane serves only for an agent that has never heartbeated: a registered-but-never-deployed agent still destroys cleanly on any account. An agent whose worker **has** come online cannot be destroyed until the feature is enabled — and because a replacement destroys before it creates, neither can it be replaced, so a change to `agent_id`, `instructions`, `display_name`, `credential_ref` or `model` (all `RequiresReplace`) now fails the apply with the old agent archived and the new one uncreated. Have Komodor support or your account admin enable `self_hosted_agent_lifecycle` before tearing down or replacing a deployed agent. Do not work around it with `terraform state rm`: re-applying the same agent id adopts the surviving agent and rotates its worker token, invalidating the Kubernetes secret already deployed in your cluster.
* resource/agentops_outpost: `allowlist` and `labels` are `Optional` only, no longer `Optional + Computed`. Removing the block from configuration now clears the value on the control plane instead of silently replanning and re-sending the previous one. Check your configuration before upgrading: an outpost whose allowlist was set out-of-band, or through an earlier apply that has since lost the block, will have it cleared on the next apply.

FEATURES:

* **New Resource:** `agentops_outpost` — full CRUD for an outpost that proxies agent traffic from a remote network, exposing the one-shot enrollment `credential` (sensitive) and its hint at creation. Supports import.
* **New Resource:** `agentops_agent` — registers a self-hosted agent and returns the rendered Helm values (`install_values`, sensitive), install command and worker-token hint for running it in your own cluster. Destroying it archives the agent first, then deletes it.
* **New Data Source:** `agentops_outpost_install` — Helm chart coordinates, values YAML, and install/upgrade commands for deploying an outpost relay.
* resource/agentops_mcp_gateway_server: Add `outpost_id`, binding an upstream's egress to an outpost tunnel instead of a direct dial from the control plane. Setting, changing and removing it bind, rebind and unbind through `PUT`/`DELETE /gateway/admin/servers/{id}/outpost`.
* **New Resource:** `agentops_self_hosted_catalog_deployment` — deploys a curated worker catalog entry into your own cluster via `POST /api/v1/worker-catalog/{catalog_id}/self-hosted-deploy`, exposing the once-only worker `token` (sensitive) and its `worker_token_hint`. Sibling to `agentops_worker_catalog_deployment`, which hosts the worker for you and exposes `repo_*` instead. Requires a user-bound API key (a PAT); a service-account token is rejected.
* resource/agentops_hosted_agent: Add `agents` attribute for delivering Claude Code subagents (`.claude/agents/*.md`) to a hosted agent, mirroring `skills`.

BUG FIXES:

* resource/agentops_mcp_gateway_server: Updating a server no longer destroys or skips its outpost binding. `UpdateServerRequest` carries no outpost field, so the update response can only echo the previous binding or null, and applying that response over the plan made every path wrong: a first bind and a rebind were skipped, and a response with a null outpost deleted a binding the configuration still asked for. The intended value is now captured before the response is applied.
* resource/agentops_mcp_gateway_server, resource/agentops_agent: A create whose follow-up call fails — the outpost bind, or the MCP-group bind — now saves the created record to state before reporting the error. The resource is tainted and replaced on the next apply instead of being orphaned in the control plane and duplicated.
* resource/agentops_agent, resource/agentops_self_hosted_catalog_deployment: A failed read after create or update no longer fails the whole apply. The read is deliberately soft (it only warns), but it left `status`, `name` and `is_archived` unknown, and Terraform rejects an unknown value after apply. For the self-hosted deployment that lost the once-only worker `token` from the applied state.
* resource/agentops_outpost: `allowlist`, `labels` and `description` can be cleared. The API leaves an omitted field alone, so removing the block from configuration was a silent no-op with no diff to show for it — an allowlist an operator believes they deleted is the wrong direction for a security control. The update now sends an explicit empty value.
* resource/agentops_credential: Rotating a credential's value no longer records stale metadata. An empty body on the re-read after the replace silently kept the pre-rotation `active_version` and `last_replaced_at`; it is an error again.
* resource/agentops_incident_pipeline: `alert_source.provider` documents the whole provider set (`datadog`, `grafana`, `alertmanager`, `pagerduty`, `opsgenie`, `generic`), not just `datadog` and `generic`. AlertManager-triggered pipelines are a primary use case and the description read as if they were unsupported.
* resource/agentops_grader_config: Restored the per-attribute descriptions that came off with the CRUD implementation, so the registry page documents the resource it still lists.
* resource/agentops_mcp_gateway_server: `static_headers` now documents the `${credential:NAME}` secret reference alongside `${env:VAR}` and `${file:path}`. The gateway has always resolved it — substituting a stored AgentOps credential by name at connect time and persisting only the reference — but the schema description did not mention it.
* resource/agentops_hosted_agent, resource/agentops_worker_catalog_deployment: `wait_for_online` now ends the wait as soon as a deploy fails, reporting the control plane's reason. The hosted-agent record's status only tracks worker heartbeats, so a provision that never produced a worker read as `draft` and the apply ran out the full `wait_timeout` before blaming the timeout.
* resource/agentops_hosted_agent, resource/agentops_worker_catalog_deployment: Deleting an agent that deployed successfully now archives it first, then waits for the archive to finish before deleting. On an account with hosted lifecycle enabled the API refuses the delete with `409 archive the agent before deleting it`, which left `terraform destroy` unable to remove what it had created. Deleting while the archive is still deploying takes a different server-side path that drops the record without revoking the agent's worker token, so the destroy fails rather than deleting early.
* resource/agentops_self_hosted_catalog_deployment: A deployment with `mcp_group_id` set can converge. The post-deploy read overwrote the planned group with whatever the agent record reported, and `mcp_group_id` is `Optional` and not `Computed`, so Terraform requires the final state to equal the plan: a deploy whose settings did not fully apply — the control plane applies them after minting the worker token and reports per-field failure in a `207` rather than rolling back — failed with `Provider produced inconsistent result after apply ... .mcp_group_id: was cty.StringVal("grp_1"), but now null`. The second apply took the same path and failed identically, so the only escape was removing the attribute from configuration. The apply now keeps the planned binding, the `207` warning names the settings that did not apply, and the next plan re-binds the group in place without rotating the worker token.
* resource/agentops_agent, resource/agentops_self_hosted_catalog_deployment: `mcp_group_id = ""` converges. `""` is what `= var.group` yields when the variable defaults to empty, and the control plane coerces the empty id to an unbind and reports `null` on the next read, so the refresh replaced the configured `""` with `null` and every subsequent plan showed the same `null -> ""` update — an apply that changed nothing and a plan that was never empty. `""` and `null` are now recognised as the same binding on refresh.
* resource/agentops_agent: Unbinding an agent's MCP group outside Terraform is detected again. The read adopted the API's `mcp_group_id` only when it was non-empty, so a group removed in the UI or by a direct API call left the stale value in state and `terraform plan` reported no changes for good, while the agent ran with no group. The refresh now reports what the API reports. A group bound outside Terraform is still not adopted while the attribute is unset — that binding is not this resource's to tear out.
